# 리뷰 서비스 포트폴리오 확장 기획

작성일: 2026-11-06

## 1. 목적과 범위

리뷰 작성·조회·수정·삭제를 기반으로, 상품을 비교하고 유용한 리뷰를 찾을 수 있는 서비스로 확장합니다. 기능 수를 늘리기보다 데이터 모델링, 권한 처리, 동시 요청 대응, 프론트 상태 관리, 운영과 검증 과정을 설명할 수 있는 결과를 목표로 합니다.

이 문서는 제안과 실행 체크리스트입니다. 체크되지 않은 항목은 구현 여부를 확정한 요구사항이나 완료된 기능을 의미하지 않습니다. 개발을 시작할 때 실제 코드·DB 스키마·배포 환경을 다시 확인합니다.

### 현재 확인한 기반

- 리뷰 CRUD와 작성 폼
- 회원가입·로그인·로그아웃 및 액세스 토큰 갱신
- 댓글·답글
- 제목·작성자 검색, 카테고리 필터, 페이지네이션
- 이미지 업로드 및 리뷰 이미지 연결·정리 처리
- 조회수와 마이페이지

위 목록은 코드에서 확인한 기능이며, 전체 사용자 흐름의 실환경 검증 완료를 의미하지 않습니다.

## 2. 진행 우선순위

| 단계 | 범위 | 완료 결과 |
| --- | --- | --- |
| 0 | 기존 기능·테스트 정비 | 주요 흐름을 반복 검증할 수 있는 기반 |
| 1 | 상품별 리뷰 모아보기 | 상품 상세에서 평점과 리뷰를 비교 |
| 2 | 도움이 됐어요 | 중복 없는 반응과 즉각적인 화면 반영 |
| 3 | 북마크 | 관심 리뷰를 저장하고 다시 조회 |
| 4 | 신고·관리자 검토 | 권한과 이력을 갖춘 운영 흐름 |
| 5 | 댓글·답글 알림 | 반응 확인 및 해당 위치로 이동 |
| 6 | 검색·조회 성능 개선 | 동일 조건에서 개선 전후 수치 비교 |

첫 공개 범위는 **0~2단계**를 권장합니다. 이후 단계는 앞 단계의 검증을 마친 뒤 추가합니다. 기능별 API 경로와 DB 컬럼명은 구현 시 기존 규칙에 맞춰 확정합니다.

## 3. 단계 0: 기존 기능과 검증 기반 정비

### 목표

새 기능을 추가했을 때 기존 인증·리뷰·댓글·이미지 기능의 회귀를 확인할 수 있도록 합니다.

### 구현 체크리스트

- [ ] 현재 페이지 → 컴포넌트 → 훅 → API → 서비스 → DB 호출 경로를 정리합니다.
- [ ] 테스트가 이전 파일 경로를 참조하는 부분을 현재 구조에 맞춥니다.
- [ ] 삭제된 동작을 검증하는 테스트와 현재 기능을 검증하는 테스트를 구분합니다.
- [ ] 인증, 리뷰 CRUD, 댓글·답글, 이미지 업로드 관련 테스트를 실행합니다.
- [ ] 로그인 → 리뷰 작성 → 상세 조회 → 수정 → 삭제 E2E 테스트를 구성합니다.
- [ ] 입력 오류, 권한 없음, 서버 오류, 빈 목록의 화면을 확인합니다.
- [ ] 프론트·백엔드 필수값과 길이 제한을 비교하고 차이를 정리합니다.
- [ ] 테스트·타입 검사·린트를 실행하는 공통 명령과 CI를 정리합니다.

### 주의점

- 테스트를 통과시키기 위해 실제 검증을 제거하지 않습니다. 오래된 경로와 잘못된 mock을 먼저 확인합니다.
- 로컬 테스트 통과와 실제 DB·이미지 스토리지·배포 환경 검증을 구분합니다.
- 프론트의 입력 제한과 별개로 서버에서도 입력을 검증합니다.
- 현재 존재하는 별도 작업과 변경 사항을 보존하고, 기능별로 변경 범위를 나눕니다.

### 완료 기준

- [ ] 검증 명령과 결과, 미검증 범위를 기록했습니다.
- [ ] 주요 사용자 흐름을 새 환경에서 재현할 수 있습니다.
- [ ] 남은 실패가 있다면 원인과 영향을 명시했으며, 통과한 것으로 보고하지 않습니다.

## 4. 단계 1: 상품별 리뷰 모아보기

### 목표와 사용자 흐름

같은 상품의 리뷰를 모아 평균 평점과 별점 분포를 확인합니다.

> 상품 검색 → 상품 상세 → 평점·별점 분포 확인 → 리뷰 비교 → 해당 상품의 리뷰 작성

### 최소 구현 범위

- 상품명·브랜드·카테고리를 가진 상품 데이터
- 리뷰와 상품의 연결
- 상품 목록·검색·상세 화면
- 상품별 리뷰 수, 평균 평점, 별점 분포, 페이지별 리뷰 목록
- 리뷰 작성 시 기존 상품 선택

### 구현 체크리스트

**데이터·백엔드**

- [ ] 현재 `product: string` 저장 방식과 실제 DB 데이터를 확인합니다.
- [ ] 상품과 리뷰의 관계를 설계하고 ERD에 반영합니다.
- [ ] 카테고리를 상품과 리뷰 중 어디에서 관리할지 정합니다.
- [ ] 기존 문자열 상품명을 상품 데이터로 옮기는 마이그레이션 절차를 만듭니다.
- [ ] 상품 검색·상세·리뷰 조회 API를 구현합니다.
- [ ] 리뷰 생성·수정 시 존재하는 상품인지 검증합니다.
- [ ] 평균 평점·리뷰 수·별점 분포 집계 쿼리를 구현합니다.
- [ ] 상품별 리뷰 조회 조건과 정렬에 맞는 인덱스를 검토합니다.
- [ ] 상품 등록 권한과 중복 상품 처리 기준을 정합니다.

**프론트엔드**

- [ ] 상품 검색·선택 UI를 작성 폼에 연결합니다.
- [ ] 상품 상세와 상품별 리뷰 목록을 구현합니다.
- [ ] 평균 평점·리뷰 수·별점 분포를 표시합니다.
- [ ] 리뷰가 없는 상품과 검색 결과가 없는 상태를 처리합니다.
- [ ] 리뷰 작성·수정·삭제 후 관련 목록과 집계를 갱신합니다.

### 주의점

- 상품명만 같다고 같은 상품으로 자동 병합하지 않습니다. 브랜드·모델·옵션의 구분 기준이 필요합니다.
- 기존 리뷰를 변환할 때 원문과 연결 결과를 확인할 수 있어야 합니다.
- 소수 평점을 허용하므로 별점 분포의 구간을 먼저 정합니다. 예를 들어 `4.0 이상 5.0 미만`과 `5.0`의 표시 방식을 문서화합니다.
- 평균 계산 대상에 숨김 리뷰를 포함할지 정하고 모든 집계에 같은 기준을 적용합니다.
- 리뷰가 0개인 상품은 평균 0점과 구분해 표시합니다.
- 처음에는 조회 시 DB 집계로 시작합니다. 집계값 저장이나 캐시는 측정된 필요가 있을 때 도입합니다.
- 외부 상품 API, 가격 수집, 쇼핑몰 연동은 초기 범위에서 제외합니다.

### 완료 기준

- [ ] 같은 상품의 리뷰만 조회됩니다.
- [ ] 리뷰 생성·평점 수정·상품 변경·삭제 후 집계가 정확합니다.
- [ ] 마이그레이션 전후 리뷰 수와 상품 연결을 검증했습니다.
- [ ] 프론트 화면과 API의 페이지·정렬·빈 결과 계약이 일치합니다.

## 5. 단계 2: 도움이 됐어요

### 목표

사용자가 유용한 리뷰에 반응하고 취소할 수 있도록 합니다. 중복 요청에도 반응 수와 사용자 상태가 일치해야 합니다.

### 구현 체크리스트

**데이터·백엔드**

- [ ] 사용자와 리뷰의 반응 관계를 설계합니다.
- [ ] `(사용자 ID, 리뷰 ID)` 조합에 고유 제약을 적용합니다.
- [ ] 반응 추가·취소 API를 구현합니다.
- [ ] 중복 추가·중복 취소의 응답 규칙을 정합니다.
- [ ] 리뷰 조회에 전체 반응 수와 현재 사용자의 반응 여부를 제공합니다.
- [ ] 동시 요청과 리뷰 삭제 시 처리 순서를 검증합니다.
- [ ] 목록의 리뷰마다 별도 쿼리를 실행하지 않도록 조회 방식을 확인합니다.

**프론트엔드**

- [ ] 반응 버튼에 선택 상태와 개수를 표시합니다.
- [ ] 요청 중 연속 클릭 처리 방식을 정합니다.
- [ ] 클릭 즉시 화면에 반영하는 낙관적 업데이트를 구현합니다.
- [ ] 실패 시 이전 상태로 되돌리고 오류를 안내합니다.
- [ ] 목록·상세의 반응 상태가 서로 일치하도록 캐시를 갱신합니다.
- [ ] 비로그인 사용자는 로그인 후 원래 리뷰로 돌아오도록 연결합니다.

### 주의점

- 프론트의 버튼 비활성화만으로 DB 중복을 방지할 수 없습니다.
- 현재 상태를 무조건 뒤집는 토글 API는 요청 재시도 시 결과가 달라질 수 있습니다. 추가와 취소를 명확하게 표현하는 방식을 우선 검토합니다.
- 반응 수를 별도 컬럼으로 저장하면 반응 행과 숫자가 어긋날 수 있습니다. 먼저 실제 반응 데이터 집계로 시작합니다.
- 본인 리뷰의 반응 허용 여부를 정합니다.
- 로그인·로그아웃·계정 변경 후 이전 사용자의 반응 상태가 남지 않도록 확인합니다.

### 완료 기준

- [ ] 같은 사용자의 동시 추가 요청 후에도 반응은 하나만 존재합니다.
- [ ] 중복 취소와 리뷰 삭제 후 처리 결과가 일관됩니다.
- [ ] 네트워크 실패 후 버튼과 개수가 서버 상태로 복구됩니다.
- [ ] 비로그인·권한 오류·세션 만료 흐름을 검증했습니다.

## 6. 단계 3: 북마크

### 목표

관심 리뷰를 저장하고 마이페이지에서 다시 확인합니다.

### 구현 체크리스트

- [ ] 사용자·리뷰 조합에 고유 제약을 둔 북마크 데이터를 설계합니다.
- [ ] 북마크 추가·취소·내 북마크 목록 API를 구현합니다.
- [ ] 현재 사용자의 북마크만 조회하도록 서버에서 제한합니다.
- [ ] 마이페이지에 페이지네이션과 빈 상태를 포함한 저장 목록을 구현합니다.
- [ ] 삭제되거나 숨겨진 리뷰의 표시 규칙을 정합니다.
- [ ] 추가·취소 후 상세와 저장 목록의 캐시를 갱신합니다.
- [ ] 중복 요청과 다른 사용자 목록 접근을 검증합니다.

### 주의점

- 도움이 됐어요와 북마크는 목적이 다릅니다. 반응 수는 공개 평가이고 북마크는 개인 보관입니다.
- 코드가 비슷하다는 이유만으로 처음부터 범용 반응 시스템으로 합치지 않습니다.
- 다른 사람의 북마크 공개는 별도 요구가 생기기 전까지 제외합니다.

### 완료 기준

- [ ] 본인이 저장한 리뷰만 확인하고 취소할 수 있습니다.
- [ ] 다른 계정으로 전환해도 이전 사용자의 저장 상태가 노출되지 않습니다.

## 7. 단계 4: 신고·관리자 검토

### 목표와 사용자 흐름

> 리뷰·댓글 신고 → 관리자 접수 목록 → 검토 → 콘텐츠 숨김 또는 신고 기각 → 처리 이력 확인

### 구현 체크리스트

**정책·데이터**

- [ ] 신고 사유와 추가 설명의 필수 여부·길이 제한을 정합니다.
- [ ] 같은 사용자의 같은 대상 중복 신고 기준을 정합니다.
- [ ] 신고 상태를 정의합니다. 예: 접수·처리 완료·기각.
- [ ] 콘텐츠 상태와 신고 처리 상태를 분리합니다.
- [ ] 처리자·처리 시각·처리 사유를 기록합니다.

**백엔드·프론트엔드**

- [ ] 리뷰·댓글 신고 API와 사용자 신고 UI를 구현합니다.
- [ ] 관리자 전용 신고 목록·상세·처리 API를 구현합니다.
- [ ] 서버에서 관리자 권한을 검사합니다.
- [ ] 관리자 화면의 상태 필터와 페이지네이션을 구현합니다.
- [ ] 숨김 처리 결과를 목록·검색·상품 집계·직접 URL 조회에 반영합니다.
- [ ] 작성자와 일반 사용자에게 보여줄 안내를 정합니다.
- [ ] 동시에 같은 신고를 처리할 때 충돌을 검증합니다.

### 주의점

- 관리자 버튼을 숨기는 것만으로 권한 검사가 완료되지 않습니다.
- 숨김은 운영상 비공개 처리이며 삭제와 구분합니다. 복구 정책과 관련 댓글·이미지 처리도 함께 정합니다.
- 신고 횟수만으로 자동 삭제하는 정책은 초기 범위에서 제외합니다.
- 검토 근거를 보존하려면 신고 대상 수정·삭제 시 무엇을 남길지 정해야 합니다. 필요한 정보만 저장합니다.
- 관리자 역할을 임의의 일반 사용자 입력으로 변경할 수 없도록 합니다.

### 완료 기준

- [ ] 일반 사용자의 관리자 API 접근이 차단됩니다.
- [ ] 허용된 상태 전이만 가능하며 처리 이력이 남습니다.
- [ ] 숨김 콘텐츠가 우회 경로로 노출되지 않습니다.

## 8. 단계 5: 댓글·답글 알림

### 목표

내 리뷰의 새 댓글과 내 댓글의 새 답글을 확인하고 해당 위치로 이동합니다.

### 구현 체크리스트

- [ ] 알림 대상·발생 조건·본인 행동 제외 여부를 정합니다.
- [ ] 수신자·유형·대상·읽음 시각을 가진 알림 데이터를 설계합니다.
- [ ] 댓글 저장 성공 후 알림을 생성하는 방식을 정합니다.
- [ ] 알림 생성 실패 시 댓글과 알림의 처리 정책을 정합니다.
- [ ] 알림 목록·읽지 않은 개수·읽음 처리 API를 구현합니다.
- [ ] 서버에서 본인 알림에만 접근할 수 있도록 제한합니다.
- [ ] 알림 목록과 댓글 위치 이동 UI를 구현합니다.
- [ ] 대상이 삭제되거나 숨겨진 경우의 이동 결과를 처리합니다.
- [ ] 재시도 시 중복 알림이 생기지 않도록 검증합니다.

### 주의점

- 처음에는 알림 목록 조회와 화면 재진입 시 갱신으로 시작합니다. 실시간 전달이 필요해지면 폴링 또는 SSE를 검토합니다.
- 이벤트 발행만으로 알림의 영구 저장과 재시도가 보장되지는 않습니다.
- 별도 트랜잭션으로 알림을 저장할 경우 누락 가능성을 설명하고, 보장이 필요한 단계에서 재시도·outbox 등을 검토합니다.
- 이메일·푸시·메시지 브로커는 초기 범위에서 제외합니다.

### 완료 기준

- [ ] 댓글 저장 실패 시 잘못된 알림이 남지 않습니다.
- [ ] 알림 읽음과 읽지 않은 개수가 일치합니다.
- [ ] 다른 사용자의 알림 조회·읽음 변경이 차단됩니다.

## 9. 단계 6: 검색·조회 성능 개선

### 목표

현재 제목·작성자 검색을 기반으로 상품 검색을 추가하고, 실제 조회 비용을 측정해 개선합니다.

### 구현 체크리스트

- [ ] 검색 범위와 일치 규칙을 정의합니다. 예: 제목·상품명·작성자, 부분 일치 여부.
- [ ] 검색 결과가 없을 때 빈 결과를 반환하는 계약을 유지합니다.
- [ ] 동일 검색 조건에서 사용할 재현 가능한 샘플 데이터를 준비합니다.
- [ ] 조회 SQL·쿼리 수·실행 계획·응답 시간을 기록합니다.
- [ ] 목록 조회와 전체 개수 조회의 비용을 각각 확인합니다.
- [ ] N+1 조회 여부와 페이지네이션 중 정렬 안정성을 확인합니다.
- [ ] 실행 계획을 근거로 인덱스·쿼리를 개선합니다.
- [ ] 같은 데이터·환경·요청 조건에서 개선 후 결과를 측정합니다.
- [ ] 평균과 p95 응답 시간, 실패율, 데이터 건수, 동시 요청 수를 함께 기록합니다.

### 주의점

- DB 종류와 검색 패턴에 따라 적절한 인덱스가 다릅니다. 인덱스 추가가 곧 성능 개선을 의미하지 않습니다.
- 한글 부분 검색과 형태소 검색은 요구사항이 다릅니다. 지원 범위를 먼저 정합니다.
- 외부 검색 엔진이나 Redis는 측정된 병목과 도입 근거가 있을 때 검토합니다.
- 무한 스크롤이나 커서 페이지네이션은 실제 탐색 방식과 데이터 증가에 따른 필요를 확인한 뒤 결정합니다.
- 로컬 부하 테스트 결과를 실제 운영 트래픽 처리 실적으로 표현하지 않습니다.

### 완료 기준

- [ ] 검색 정확성과 빈 결과 처리를 유지했습니다.
- [ ] 측정 조건과 개선 전후 수치를 함께 공개할 수 있습니다.
- [ ] 개선 이유, 비용, 적용하지 않은 대안을 설명할 수 있습니다.
